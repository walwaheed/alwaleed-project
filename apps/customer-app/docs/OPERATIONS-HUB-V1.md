# Customer Operations Hub V1 — Prototype Notes

## ما تمت إضافته

تمت إضافة تبويب خدمات عربي موحد يضم الحجز، الطباعة، رفع الصور، فحص الجواز والفيزا، الصور الشخصية، طلبات الشركات، تتبع الطلب، الدفع، عروض الأسعار، والمساعدة. كل بطاقة تقود إلى شاشة قصيرة ذات خطوة تالية واضحة، مع نماذج محلية مبسطة للطلبات التي تحتاج إدخالًا.

## الحدود الحالية

المشروع ما زال نموذجًا أوليًا. جميع الأسعار، حالات الطلب، الدفع، الحجز، عروض الأسعار، ونتائج التحليل بيانات وهمية. لا يتم إنشاء سجل عميل حقيقي، ولا يتم إرسال ملف أو تشغيل دفع أو تعديل أي نظام خارجي.

## عقود API المستقبلية

| العملية | المسار المقترح | مصدر الحقيقة لاحقًا |
|---|---|---|
| إنشاء حجز | `POST /bookings` | Supabase عبر API Gateway |
| إنشاء طلب | `POST /orders` | Supabase |
| رفع ملف | `POST /uploads` | Storage عبر API Gateway |
| إنشاء عرض سعر | `POST /quotations` | Supabase / مراجعة المالك |
| حالة الدفع | `GET /payments/:id` | Moyasar بعد تحقق الخادم |
| بدء الدفع | `POST /checkout` | API Gateway ثم Moyasar |
| المنتجات | `GET /products` | كتالوج قابل للتكوين |
| تتبع الطلب | `GET /order-status/:reference` | Supabase / fulfillment |
| طلب شركة | `POST /corporate-request` | n8n ثم GHL |

## حدود الأمان

يجب أن تبقى مفاتيح Moyasar وSupabase وGHL وn8n وWindmill على الخادم. لا يقرر التطبيق نجاح الدفع، ولا يعرض بيانات داخلية أو حقول قاعدة البيانات أو أسرار webhooks. قبل الإنتاج يجب إضافة التحقق من الملفات، تحديد معدل الطلبات، تقليل بيانات الهوية، سجل تدقيق، ومصادقة منفصلة للموظفين.

## ترتيب Phase 2 المقترح

يبدأ الربط ببوابة API موحدة للمنتجات والحجوزات والطلبات، ثم رفع الملفات، ثم تحقق الدفع، ثم حالات fulfillment والإشعارات، ثم عروض الأسعار وطلبات الشركات، وأخيرًا تحليلات المالك. يظل Manus مسؤولًا عن تجربة المستخدم ومسار العميل، بينما تبقى الحقيقة التشغيلية والمالية في الأنظمة المخصصة لها.
