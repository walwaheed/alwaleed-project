## 2. Frozen six-endpoint contract

The six endpoints below are the canonical V1 surface. No duplicate endpoints are created.

### 2.1 `GET /api/cloudprinter/products`

Despite its path name, this endpoint is the frozen catalog surface for the first print-provider implementation. The response must be normalized into the `Product` schema before reaching the UI. The path can later be retained as a compatibility route while the backend internally moves toward a provider-neutral catalog.

**Request:** query parameters `product_type`, `locale`, and optional `country`.

**Response:** `{ products: Product[], catalog_version: string, fetched_at: string }`.

**Error:** `PRODUCT_CATALOG_UNAVAILABLE` or `PRODUCT_NOT_FOUND` using the standard error contract.

### 2.2 `POST /api/upload`

**Request:** multipart file plus `purpose`, `customer_id` or guest session reference, and an idempotency key. The UI sends the explicitly selected file only.

**Response:** `{ upload: Upload }`.

**Error:** `UPLOAD_INVALID_TYPE`, `UPLOAD_TOO_LARGE`, `UPLOAD_DIMENSIONS_INVALID`, or `UPLOAD_STORAGE_UNAVAILABLE`.

### 2.3 `POST /api/cloudprinter/quote`

**Request:** `{ customer_id, items: [{ product_id, quantity, upload_ids }], destination?: { country, city }, currency: "SAR" }`.

**Response:** `{ quote: Quote }`.

**Error:** `QUOTE_EXPIRED`, `PRICE_CHANGED`, `PRODUCT_UNAVAILABLE`, or `FULFILLMENT_UNAVAILABLE`.

The endpoint name remains unchanged for compatibility. Its response must be a provider-neutral Quote rather than exposing raw Cloudprinter internals.

### 2.4 `POST /api/print-orders/create`

**Request:** `{ customer_id, quote_id, items, upload_ids, contact, idempotency_key }`.

**Response:** `{ order: Order, next_action: "PAYMENT_REQUIRED" | "TRACK_ORDER" }`.

**Behavior:** the server revalidates the quote, amount, product availability, customer identity, and upload ownership. The UI cannot set order status or payment status.

**Error:** `QUOTE_EXPIRED`, `PRICE_CHANGED`, `ORDER_CREATE_FAILED`, `DUPLICATE_REQUEST`, or `UPLOAD_NOT_READY`.

### 2.5 `POST /api/payments/moyasar/create-invoice`

**Request:** `{ order_id, return_url, cancel_url, idempotency_key }`.

**Response:** `{ payment: Payment, checkout_url: string }`.

**Behavior:** the server reads the amount and currency from the existing order. The client never supplies an arbitrary amount.

**Error:** `PAYMENT_CREATE_FAILED`, `ORDER_NOT_PAYABLE`, or `PAYMENT_ALREADY_EXISTS`.

### 2.6 `GET /api/print-orders/status/:id`

**Request:** path `id` is the canonical order ID or an explicitly agreed order-number mapping. The backend must not accept an ambiguous identifier silently.

**Response:** `{ order: Order, payment_verification: PaymentVerification, fulfillment: Fulfillment | null, tracking: Tracking }`.

**Behavior:** payment state is read from backend verification; order and fulfillment state are read from their existing systems.

**Error:** `ORDER_NOT_FOUND`, `ORDER_ACCESS_DENIED`, or `STATUS_UNAVAILABLE`.

### Endpoint shape changes

No endpoint is added or removed. Two normalization requirements are mandatory before implementation: the product and quote endpoints must return provider-neutral fields to the UI, and the status endpoint must return verification, fulfillment, and tracking objects together. These requirements prevent Cloudprinter and payment-provider details from leaking into the customer experience.

## 3. Payment state machine

| state | customer message | allowed actions | retry behavior | order preserved | fulfillment blocked | next best action |
|---|---|---|---|---:|---:|---|
| `UNPAID` | الطلب جاهز للدفع | بدء الدفع، تعديل الطلب، إلغاء | Create a new invoice | yes | yes | ابدأ الدفع |
| `PENDING` | نتحقق من عملية الدفع | انتظار، تحديث الحالة، التواصل مع الدعم | Do not create repeated invoices immediately | yes | yes | انتظر التحقق |
| `PAID` | تم تأكيد الدفع | عرض الطلب، متابعة الحالة | No payment retry | yes | no | تابع الطلب |
| `FAILED` | لم تنجح عملية الدفع | إعادة المحاولة، تغيير الطريقة، تعديل الطلب | New invoice after server confirms failure | yes | yes | أعد المحاولة |
| `CANCELLED` | ألغيت عملية الدفع ولم يتم الخصم | العودة للدفع، تعديل الطلب، الإلغاء | New invoice allowed | yes | yes | اختر متابعة الدفع أو عدّل الطلب |
| `EXPIRED` | انتهت جلسة الدفع | بدء جلسة دفع جديدة، تعديل الطلب | New invoice allowed | yes | yes | ابدأ جلسة جديدة |

Only verified backend status can transition to `PAID`. The frontend never performs this transition.

## 4. Order state machine

| current state | allowed trigger | next state | owner |
|---|---|---|---|
| `DRAFT` | create order with valid quote | `PENDING_PAYMENT` | Order API |
| `PENDING_PAYMENT` | verified payment | `PROCESSING` | Payment verification + Order API |
| `PENDING_PAYMENT` | customer cancellation or expired payment | `CANCELLED` or remain payable | Order API |
| `PROCESSING` | fulfillment submission accepted | `SUBMITTED_TO_PROVIDER` | Fulfillment router |
| `SUBMITTED_TO_PROVIDER` | provider ships | `SHIPPED` | Provider adapter |
| `SHIPPED` | delivery confirmed | `DELIVERED` | Shipping/tracking |
| any non-delivered state | approved cancellation policy | `CANCELLED` | Order service |

The UI may request an action. It never assigns the next state.
